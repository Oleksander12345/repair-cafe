# 0001. Модульний моноліт з машинно перевірними межами

- Статус: accepted
- Дата: 2026-10-05

## Контекст і проблема

Застосунок нарощується п'ять лаб поспіль (БД, тести, CI, перформанс). Потрібна структура, яка не
розвалиться до кінця семестру і в якій межі модулів не тримаються лише «на чесному слові».

## Драйвери рішення

- Межі модулів перевіряються автоматично, а не на рев'ю.
- Доменні правила (машина статусів, навички майстрів) тестуються без HTTP і БД.
- Мінімум інфраструктури: одна команда, один процес, один розробник.

## Розглянуті варіанти

1. Шари по всьому проєкту: `controllers/ services/ repositories/`
2. Модульний моноліт: `modules/<фіча>/{domain,service,ports,index}` + правила dependency-cruiser
3. Мікросервіси (tickets / volunteers окремо)

## Рішення

Обрано **варіант 2**: зміна однієї фічі торкається однієї папки, а правила R1–R5 (spec §1) ловлять
порушення до пушу.

### Наслідки

- Добре: аудит Лаби 1 знайшов реальні порушення саме завдяки правилам (docs/audit-lab1.md).
- Добре: `ports.ts` дає шов для Лаби 2 — статичні дані → БД без змін у сервісах.
- Погано: більше файлів і явних інтерфейсів, ніж потрібно для MVP.
- Як перевіряємо: `make deps` (C-06…C-13), запускається на pre-push.

## Плюси і мінуси варіантів

### Шари по проєкту

- Добре: звично, мало папок.
- Погано: фіча розмазана по 3 папках; «сервіс тікетів лізе в репозиторій волонтерів» не ловиться жодним правилом.

### Мікросервіси

- Добре: жорсткі межі на рівні мережі.
- Погано: «перевір навичку + візьми річ» стає розподіленою операцією; мережа, деплой, контракти — не мета курсу.
