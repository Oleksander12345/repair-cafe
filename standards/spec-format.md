# Стандарт: формат spec

**Навіщо.** Spec — контракт, проти якого ведеться аудит. Якщо критерій не можна перевірити,
аудит перетворюється на думку. Тому spec коротка і кожен критерій — перевірний.

## Правила

1. Один файл `spec.md` у корені, **≤ 1 сторінки** (≈ 60 рядків тексту без діаграм).
2. Обов'язкові розділи, саме в такому порядку:
   1. **Що і навіщо** — 1–2 речення + головний інваріант системи.
   2. **Модулі та межі** — таблиця «модуль / відповідальність / може залежати від» + правила меж `R1..Rn`.
   3. **Дані** — ER-діаграма (Mermaid) + інваріанти полів.
   4. **Як дані оновлюються** — для кожного ключового сценарію: кроки, точки помилок (коди), межі транзакцій.
   5. **Критерії прийняття** — чекбокси `ACn`.
3. Кожен `ACn` має **спосіб перевірки** (команда `make …`, тест або правило). Критерій без перевірки не приймається.
4. Кожне правило меж `Rn` має **машинну перевірку** (dependency-cruiser / ESLint). Межа, яку ніщо не перевіряє, — побажання, а не межа.
5. Spec змінюється **окремим комітом** `spec: …` _до_ коду, що її реалізує. Якщо аудит знайшов розбіжність — спершу правка spec/стандарту, потім код.
6. Розбіжність код ↔ spec, знайдена пізніше, фіксується в `docs/audit-labN.md` з посиланням на коміт.

## Чому не довше

Довга spec не читається на рев'ю за 5 хвилин і швидко застаріває. Деталі реалізації — у коді й ADR, не тут.
